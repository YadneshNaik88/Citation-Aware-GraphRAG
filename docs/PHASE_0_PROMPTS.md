# PHASE_0_PROMPTS.md: Antigravity task prompts for Phase 0

How to use: one task per agent session and one branch per task. Start every prompt with:

> Read AGENTS.md, docs/ARCHITECTURE.md and docs/PROTOCOL.md first and follow them strictly. If anything cannot be verified, write it to OPEN_QUESTIONS.md and stop that sub-task. Do not start any other task.

Antigravity setup (verify against Google's current Antigravity docs; the details below come from third-party guides): the workspace rules location is reported as `.agents/rules/` (older `.agent/rules/` also works) or a root-level `AGENTS.md`/`GEMINI.md`, with a reported cap of 12,000 characters per rules file. This repo's `AGENTS.md` is kept under that cap. If rules do not appear in the agent's context, paste `AGENTS.md` into the workspace rules panel instead.

Suggested owners (not machine assignments): T0.1 M1, T0.2 M1 with M3, T0.3 M2, T0.4 M4, T0.5 everyone. Each task needs a reviewer from another member.

Before starting: each member that will call OpenAlex creates a free API key at openalex.org (account settings) and exports it as an environment variable. Do not paste keys into prompts or files.

## T0.2 OpenAlex API pilot (answers the open [?] items)
Write `src/common/openalex_client.py` (key from env, rate limiter, exponential backoff, hash-keyed compressed cache that excludes the key from the hash, spend ledger, `--max-cost-usd` and `--max-calls` guards, replay mode) with unit tests using recorded fixtures. Then write `scripts/pilot_openalex.py` and answer, from real responses only:
1. Does `group_by` work for works on `primary_topic.id`, `primary_topic.subfield.id`, `topics.id` and `publication_year`, with and without a filter such as `publication_year:2019`? Page size, cursor behaviour, and the number of calls needed to get topic-by-year counts for the full range.
2. Can unordered topic co-assignment counts be obtained, for example by filtering on one `topics.id` and grouping by `topics.id`? Record whether the filter uses primary topic or any of up to three topics.
3. Is there a supported random-sampling option for works (check the official docs, then test with a fixed seed for reproducibility)? If not, document the citation-agnostic deterministic alternative.
4. Direction and semantics of the `cites`, `cited_by` and `referenced_works` filters, verified on one known pair of papers.
5. Real cost and latency per 1,000 records (list calls with `select=` and `per_page=100`), cost of keyword search and of `search.semantic` (read `/rate-limit` before and after), and observed rate-limit behaviour.
6. Share of works with abstracts by field and year (small sample), accepted `type` values, `language` field behaviour, publication-date granularity.
7. Duplicate rate (same DOI or same normalised title and year) in a small sample; frequency of citing/cited date anomalies (cited paper dated later than citing paper).
8. How to dump the topic taxonomy (topics, subfields, fields, domains) and compute a content hash.
9. Behaviour of the default exclusion of expansion-corpus works and any flag that reveals it.
**Acceptance:** `docs/results_notes/T0.2_api_pilot.md` with a table of every answer, each tied to a cached response ID; a total pilot spend figure from the ledger; anything unverified listed under OPEN_QUESTIONS.md. Stay far below the free daily allowance; stop if usage exceeds the guard.

## T0.3 Embedding benchmark (measures whatever machine runs it)
Write `scripts/benchmark_embed.py` and `configs/benchmark.yaml`. **Data requirement:** the benchmark needs 1,000–2,000 real abstracts (title + abstract, empty string if missing), obtained only through the shared OpenAlex client so every call is cached, ledgered and budgeted. First count the usable abstracts (non-null `abstract_inverted_index`, rebuilt text of non-trivial length) already in the T0.2 pilot cache. If there are at least 1,000, use them. If not, this prompt **authorizes one separate bounded acquisition**, run by `scripts/acquire_benchmark_abstracts.py`, under these limits: at most 100 calls and at most US$0.05 (at the listed list-call price of about US$0.0001 per call, 2,000 records is roughly 20 calls; confirm the actual cost from the ledger), `per_page=100`, `select=` only the fields needed, a fixed filter such as `has_abstract:true` plus a stated year range, a citation-agnostic deterministic or seeded selection (never ordered by citation count), the same year/field spread as documented in the script, and no retries beyond the client's backoff. Record the request hashes, spend, selection rule and date in `data/manifests/` and in `docs/results_notes/T0.3_data_acquisition.md`. Any need beyond these limits requires a written approval from a team member in `OPEN_QUESTIONS.md` before running. **Never fabricate, synthesize (including LLM-generated text), duplicate, or silently substitute records from another source.** If fewer than 1,000 usable abstracts are available after the authorized acquisition, run the benchmark on what exists, report the actual `n`, and flag the reduced sample as a limitation. These abstracts are for speed and memory measurement only: tag them `origin: benchmark`, and never include them in an evaluation build. Then load `allenai/specter2_base` with the `adapters` library, attach `allenai/specter2` as the proximity adapter and `allenai/specter2_adhoc_query` as the query adapter; follow the model cards for the input format (title + separator token + abstract, truncation to 512 tokens, first-token hidden state) and verify these details from the model cards you actually load, do not copy them from this prompt. Record: machine description (CPU, RAM, GPU if any, from system calls, not assumed), embedding dimension read from the model config, parameter count, throughput (papers per second) by batch size and max length (256 and 512), peak memory (system and GPU), fp32 vs fp16 speed, cosine similarity between fp16 and fp32 embeddings and the top-10 neighbour overlap, and a check that switching between the two adapters in one process gives the correct outputs (encode a query, then a document, then the same query again and compare). Extrapolate hours per million abstracts per setting and label it as an extrapolation.
When this task first adds PyTorch, `transformers`, `adapters` and their dependencies, pin them exactly as in AGENTS.md section 4 (regenerate `requirements-lock.txt`, document the CPU or CUDA build used in `docs/ENVIRONMENT_NOTES.md`), and record the exact Hugging Face revision (commit hash) of the base model and each adapter that was loaded.
**Acceptance:** `docs/benchmarks.md` generated from `runs/`; every figure traceable to a run; the actual number of abstracts used, where they came from (pilot cache or the authorized acquisition) and the acquisition spend stated; model revisions and package versions recorded; the estimates in PROTOCOL.md section 10 compared with the measurements; limitations listed.

## T0.4 Build manifest schema and leakage-audit skeleton
Define a build-manifest schema (YAML or JSON with a validating test): build ID, harvest window start and end (`D_snap`), taxonomy hash, `T_cut`, label window, API parameters, fixed type filter, model and adapter versions, software versions, replay-only flag. Implement `src/common/time_guard.py` with tested functions: `is_visible(d_pub, t_cut)`, `edge_visible(d_pub_a, d_pub_b, t_cut)` (both endpoints), year-only date handling (31 December), a consistency check that `D_snap` is later than the end of the label window, and a chronology-anomaly detector. Implement `tests/test_leakage.py` and `configs/leakage.yaml` (lists the feature-building paths, the display-only path allowlist, and the forbidden present-day citation fields: `cited_by_count`, `counts_by_year`, `fwci`, citation percentiles). Policy to encode: present-day citation measures are **prohibited in predictive feature-building code** (anything under the configured feature paths, plus sampling, label, ranking and training code) but **allowed as display-only metadata** for descriptive reporting and the interface, stored under `display_`-prefixed columns. The tests must therefore:
1. Statically scan the configured feature-building paths and fail on any forbidden field, any read of a `display_`-prefixed column, or any import of display-only modules. The same fields in allowlisted display or reporting modules must pass.
2. Check feature tables at runtime: each feature column declares its source tables and `max_source_date`; fail if any exceeds `T_cut`, if a `display_` column is present, or if a label-window quantity (`f`, `E_f`, label-window marginals) appears as a feature.
3. **Truncation-invariance test (detects future-derived features):** build features for cutoff `T` from the full fixture, rebuild them from a copy with every record or edge with `d_pub > T` (or an invisible endpoint) removed, and require identical output. Also rebuild after modifying only post-`T` records and require unchanged features. Any difference means the feature uses future information.
4. Check graph and index inputs: no node with `d_pub > T_cut`, no edge with an invisible endpoint, taxonomy hash equals the manifest, `D_snap` later than the label-window end.
5. Check that a live API call in an evaluation (replay) run fails.
Fixtures: one clean fixture that passes; leaky fixtures that must each fail: future node, edge with an invisible endpoint, `cited_by_count` in feature code, a `display_` column read by feature code, a feature computed from post-`T` counts, a feature containing `E_f`, and a live API call in replay mode; plus one fixture where `cited_by_count` is used only in an allowlisted display module and must pass. Wire `make leakage`.
**Acceptance:** all tests pass; each leaky fixture is caught and the display-only fixture is allowed; CI runs `make leakage`.
